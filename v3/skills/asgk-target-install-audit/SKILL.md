# Target adoption assessment

A human selects the capable evaluator outside ASGK. The Skill guides its attention,
not its conclusion. Start from the target's minimal startup set and actual governance
practice; source docs/INSTALL_SURFACE.md supplies comparison responsibilities.

Identify target purpose, risks, existing authorization/review/handoff/decision retrieval,
and equivalents before declaring gaps. Evaluate whether GitHub-native projections or
persistent roles help this target; no Bot platform, model, source filename or directory
layout is mandatory. A missing ASGK-named file is not a missing capability.

Use target-evidence-check only for caller-supplied mechanical path/text claims.
Judge minimum sufficient adaptation, no change or no adoption using evidence,
alternatives, confidence, unknowns, compatibility and rollback. Do not impose module
selection or a universal human gate for semantic evaluation.

Record the assessment in a target-owned issue/PR. Its outcome is assessment_complete
or blocked, not adoption approval. Name an existing next_action_gate only for the exact
proposed high-risk operation. Implementation requires separately bounded target scope;
preserve target status, navigation, policy, license, history and output ownership.
